# Tracker, evidence, and dependency validation contract

`docs/PORTING_TRACKER.json` is authoritative; `docs/PORTING_CHECKLIST.md` is an exact human projection. Every substantive and `.V` record has a literal, ordered `dependencies[]`. Edges name complete stable item IDs only. The validator rejects missing records, unknown, duplicate, self, and cyclic edges, and `.V` records that do not directly close over every substantive child.

`readiness` is derived, never asserted: a root is `ready`; a non-root is `ready` only when every dependency is `[x]`, each cited evidence record and required review/adoption is current, approved, hash-reachable, unexpired, and unaffected by an invalidation edge. Otherwise it is `blocked`. A record may become `[-]` only from `[ ]` with owner, branch/PR, date, and current evidence. `[x]` additionally requires ready dependencies, passing evidence, closed review, and approved adoptions. `[D]` is legal only for an external blocker with owner, immutable evidence, unblock condition, decision record, and current validity review. Returning to `[ ]` is required when a blocker becomes actionable or evidence/review/adoption becomes stale.

Parent/chunk state is derived from all substantive children and its `.V`: complete only when all are `[x]`; externally blocked only when at least one valid `[D]` exists and none is active; in progress when any child is `[-]` or `[x]`; otherwise not started. Parent prerequisites are metadata and never edges.

Evidence conforms to `evidence-v1.schema.json`, is immutable, and binds a full `subject_revision`: the clean committed code/governance candidate on which the command ran. An EV envelope may be committed only in a descendant of that subject. It records exact subject blob SHA-256 values and Git modes for every relied-on artifact and transitive input, plus exact command, normalized environment/toolchain, run/case IDs, timestamps, results, stdout/stderr, and generated artifact hashes. Validation rejects expired or superseded evidence, self-hashes, cycles, unknown or duplicate normalized paths, and any subject-artifact reference outside the governed closure.

Reviews conform to `independent-review-v1.schema.json` and use the same non-circular `subject_revision`. Review envelopes, findings, and post-fix rerun envelopes may be committed in descendants. Every finding's `fix_revision` is a full commit containing the fix, is an ancestor of the subject reviewed for closure, and is followed by subject-bound passing reruns whose exact artifact hashes are covered. Approval still requires authenticated authorship/ownership, a disjoint independent reviewer set, one closure reviewer, zero unresolved findings, unexpired retention, and exact architecture/security/license artifact sets.

Dependencies and tools are adoption instances, not globally pre-approved. Each consuming item lists the exact current inventory identifiers; every instance binds one consuming item, its real local `.V` gate, a current `DD-###`, source/version/features, and security and license dispositions. Unknown, reused, wrong-owner, rejected, pending, retired, unregistered, digest-drifted, obsolete, duplicated, or incomplete tracker `AD-####` projections block effective completion. Clean cutover is mandatory: remove superseded IDs and atomically replace each tracker `adoptions[]` array with the inventory's complete current set for that consumer; aliases and compatibility references are forbidden. Inventory-only and repository-input decisions register C000 inputs but do not invent approval for later production dependencies. C000 adoption discovery includes C000.12, DR-004, the pinned `java-tron/example/actuator-example`, and the exact custom-actuator provenance inputs `java-tron/example/actuator-example/build.gradle` and `java-tron/example/actuator-example/src/main/java/org/tron/core/actuator/ExampleActuator.java`. The platform and oracle manifests are descendant attestation envelopes, not dependency-adoption inputs: adoption discovery, `generated_from`, instances, and dependency decisions must exclude them. Evidence, review, tracker, checklist, and any other descendant attestation artifacts are likewise forbidden from adoption discovery; real tools, schemas, fixtures, policies, ownership ledgers, Cargo manifests, and other governed repository inputs remain discoverable.

Effective completion is stricter than the stored checkbox. A record is effectively complete only when it is `[x]`, every dependency is effectively complete, every evidence and adoption reference is current and owned by that record, and every record-specific predicate passes. C000.08 and C000.09 additionally require fresh, source-revision-bound ownership ledgers whose declared row counts, unique IDs, tracker owners, gates, generator digest, and fail-on-unknown policy recompute correctly. C000.12 additionally requires DR-004 and both exact checked-in custom-actuator provenance artifacts in adoption discovery and in the license review's exact artifact set and scope. C000.14 additionally requires the complete native platform predicate. C000.V additionally requires all three approved review classes, the ledger/adoption/projection predicates, and C000.14 platform completeness. Readiness and downstream completion are derived from this effective state, not from local checkbox values.

The external immutable authorization ref is `refs/tags/c000-subject`. It must exist as an SSH-signed annotated tag object that directly targets one available full 40-hex commit object; lightweight tags, nested tag targets, missing objects, abbreviated identities, ambiguous peeling, and non-SSH signatures are rejected. Authorization has no fallback: local repository Git config must define `gpg.ssh.allowedSignersFile` and `gpg.ssh.revocationFile` as existing files inside the project, and `port.c000SubjectTagObject` as the exact 40-hex annotated-tag object ID currently named by the ref. The validator runs `git verify-tag` on that pinned object, so absent, mismatched, unsigned, untrusted, revoked, expired, or replaced tags fail before their target can authorize a subject. Both platform and oracle manifests must exactly equal the direct commit target. The authorized subject must be an ancestor of `HEAD`; shallow history, grafts, and replacement objects are rejected. The manifests bind the exact governed input closure at that commit with `git-ls-tree-v1` and, as descendant attestation envelopes, are not members of the closure they attest. The validator hashes committed blob bytes, executable/symlink modes, and submodule links at the subject and requires the identical closure at `HEAD`. The only excluded descendant changes are the two attestation manifests, EV/RV envelopes and their committed output artifacts, tracker/checklist status projection, and commit metadata. Added, removed, renamed, content-changed, mode-changed, symlink-changed, submodule-changed, or otherwise unclassified governed paths fail closure identity.

Authorization rotation is an explicit policy operation, never a retag. Create and review a new SSH signing key or validity window in the project-local allowed-signers file; add compromised or retired keys to the project-local revocation file; create a new SSH-signed annotated authorization tag under a new immutable ref name that directly targets the newly approved subject; verify it with the same local Git configuration; pin its exact tag object ID in local `port.c000SubjectTagObject`; update this contract and both manifests to name the new authorization ref and target; then remove the old ref from active policy without rewriting its object. Emergency revocation first updates the revocation file and removes the signer from the allowed-signers file, which makes validation fail closed until the complete reviewed rotation is installed. Expired signer windows are rotated by the same procedure. Reusing `refs/tags/c000-subject`, force-updating any authorization tag, changing only the object pin, or accepting an unpinned/ref-only target is prohibited.

The platform manifest enumerates every initially supported row and separately reserves later-enablement rows without treating them as C000 evidence claims. Coverage totals and result are recomputed from the support scope, rows, current evidence, and reviewed non-applicability; checked-in counters are assertions, not inputs. `F-PRODUCTION-DEFAULT` is the exact set of Cargo features declared by the workspace (currently the empty set), not a synthetic feature named `default`. A passing native cell must resolve current C000.14 evidence binding the exact cell command and working directory, target triple, native host OS/architecture and execution, required toolchains, backend, complete feature set, platform row, and cell identity. A `not_applicable` cell additionally requires current evidence whose review bindings include every approved independent review named by the cell, plus a concrete review scope and reopen condition. Runnable cells without current bound evidence and all deferred, unavailable, cross-built, emulated, unreviewed-not-applicable, or otherwise unrun applicable cells remain incomplete. Reserved later-enablement rows do not satisfy or block C000; promoting one to initial support requires a reviewed manifest change and its full native cell evidence.

`tools/tracker/validate.py` is dependency-free and never mutates status. It rejects staged, unstaged, untracked, submodule-drifted, shallow, grafted, or replacement-object states; requires the pinned SSH-signed annotated authorization tag and project-local trust/revocation configuration described above; requires both manifests to exactly match its direct full-commit target; verifies exact ancestry and closure identity from subject to committed `HEAD`; and validates the platform/oracle manifests and EV/RV descendant attestations against committed subject and descendant blobs and modes rather than mutable worktree bytes. The subject tree's `java-tron` entry must be a `160000` gitlink whose exact object ID equals the oracle manifest's full `java_source_revision`. Every requested `java-tron/<path>` adoption, review, evidence, or invalidation subject input is resolved as a blob and mode from that exact commit through the initialized submodule's local Git object database, never from mutable worktree files; missing, unavailable, shallow, non-commit, checkout-drifted, or mismatched submodule objects and non-canonical or escaping paths are rejected. Subject inputs are a separate domain from descendant outputs: every `subject_artifacts` entry and every invalidation edge must resolve to the authorized subject closure (including this pinned gitlink domain) and must not name an attestation/evidence/review path, while evidence `stdout`, `stderr`, and `artifacts` may name such paths only when the path is absent from the subject, is committed in the descendant `HEAD`, is under an evidence directory, is a blob, and exactly matches the declared SHA-256. An output can never be reused as a subject or invalidation input. This separate attestation contract validates manifest contents against the authorized subject closure without feeding either manifest back into adoption or governed-closure discovery. It rejects self-reference, forbidden attestation/adoption inputs, unknown paths, duplicate paths, superseded/expired records, stale reruns, unresolved findings, reviewer/author/owner overlap, incomplete C000.12 custom-actuator license/provenance coverage, and obsolete tracker adoption projections with clean-cutover guidance, then derives effective completion from the remaining current records.

The deterministic C000 artifact audit is `tools/platform/run c000-artifacts`. It is a read-only inspection of the workspace: it does not start either node, create evidence, or mutate the tracker/checklist. Its canonical, key-sorted JSON contains one emitted case for each of C000.01-C000.12 and C000.15 plus C000.V; every case reports pass/fail, observations, and the path/SHA-256 identity of each artifact actually inspected. Missing or malformed documents fail their owning case. The ledger cases inspect only the current source-derived `production-ownership.v1.json` and `java-test-ownership.v1.json` contracts, never the superseded legacy ledger snapshots. C000.04 recomputes the oracle manifest's revision, referenced schemas, fixtures, implementations, ledger identities/counts/digests, and regeneration contract; its free-form `status` text is not proof. C000.15 applies the validator's current adoption-instance model, including generated-input digests, consumer/local-gate/decision bindings, source digests, and security/license dispositions.

C000.V is aggregation, not node behavior. In addition to every emitted substantive audit case passing, it internally applies the same current evidence, independent-review, and native-platform predicates used by the tracker validator to C000.13 and C000.14. C000.13 requires current passing evidence owned by C000.13. C000.14 requires current passing evidence with exact command, working-directory, target, native host/execution, toolchain, backend, feature-set, platform-row, and cell bindings, plus recomputed complete coverage for every initially supported platform cell. Reviewed non-applicability requires current bound approval, an empty evidence list, and explicit review scope and reopen conditions. C000.V separately requires exactly one current architecture, security, and license approval class owned by C000.V; approvals bind the checked revision, registered independent closure reviewer, resolved findings and required passing reruns, retention, and exact covered-artifact hashes. Tracker/checklist status fields and checkboxes are never accepted as artifact proof. The command exits zero only when every emitted case and these internal semantic predicates pass, and otherwise exits one while still emitting the complete audit JSON.
