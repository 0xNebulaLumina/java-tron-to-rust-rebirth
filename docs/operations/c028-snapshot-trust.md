# C028 snapshot trust and recovery

Accept snapshots only from local files after offline DSSE verification against the `snapshot:<network>` role with the exact canonical `snapshot:<network>` trust-role scope. A role-name match never substitutes for scope binding: empty, mismatched, and cross-network scopes are rejected before import mutation. Require threshold signatures, exact network/genesis/backend/schema/features, payload size and SHA-256, source release, explicit verification time, freshness (maximum 604800 seconds; future skew 300 seconds), minimum height and monotonic trust-store version/watermark. The independently authenticated operator checkpoint is mandatory in production and must use a non-zero height plus non-placeholder 32-byte block ID and state root. Snapshot acceptance requires the signed manifest height, block ID, and state root to equal that operator checkpoint tuple exactly; a newer signed snapshot is unrelated evidence and is rejected unless the operator first advances the independently authenticated checkpoint.

Trust stores are root-owned, no-follow inputs and are not release subjects. A rotation must be exactly version +1 and satisfy both current and candidate root thresholds. Revoked, expired, duplicate or unknown signers do not count. Never fetch a missing payload, key, trust store or Sapling parameter during verification.

Bootstrap snapshot roots out of band from independently authenticated operator channels and pin the canonical digest in root-owned deployment state before accepting any snapshot. Snapshot payloads and snapshot release artifacts may include a dual-signed rotation envelope, but never the authoritative trust root used to verify themselves. Verify each version+1 rotation under the installed current root before writing the new root, update the root and watermark atomically, and retain the preceding root for audited recovery. For revocation, stop imports, require the remaining current threshold and the new threshold over a store that removes the compromised key, then advance the minimum trusted version. If the current threshold is lost, require explicit offline re-bootstrap; never recover by trusting a root found beside the candidate snapshot.

During import, `tron-storage.snapshot-bootstrap.json` is a not-ready condition. After restart, recovery must finish or clean the journal, then agree on generation root, `tron-storage.snapshot-provenance.json` and `tron-storage.snapshot-watermark.json` before readiness. Provenance and watermark retain the exact accepted height/block-ID/state-root tuple, which is the independently trusted checkpoint because acceptance forbids descendant-by-height substitution. Preserve the previous generation. On corruption, rollback height, stale metadata or incompatible identity, leave the destination byte/metadata-identical; do not repair or initialize silently.
