# C028 release verification

Build only from a clean source revision with the pinned Linux x86_64 builder, locked/offline Cargo inputs and `SOURCE_DATE_EPOCH` equal to the commit timestamp:

The production OCI shell is an explicit offline input, never an apt-installed runtime or `PATH` discovery result. `docs/oracles/c028-busybox-material.v1.json` fixes the exact source-package URL/digest, extracted member, material digest, version marker, SPDX license and provenance URI. The generator accepts only `TRON_BUSYBOX` as the material path, compares its bytes with that repository policy, and parses the ELF64 header and program headers itself to require x86-64 static linkage and the embedded version marker. It never executes BusyBox and never delegates trust to `file(1)`. The verified digest and identity remain bound into the signed release manifest, SPDX package record, SLSA material list, and OCI layer.

The candidate build job initializes recursive submodules, runs the immutable java-tron guard, downloads only the repository-pinned BusyBox package, verifies both package and extracted-material digests, and performs all release-binary, reproducibility, OCI and clean-install execution without signing secrets. The publish workflow does not download or materialize BusyBox.

```sh
TRON_BUSYBOX=/absolute/offline/policy-matching-busybox python3 tools/release/c028_release.py build --out release-A --release-id RELEASE --version VERSION --release-sequence N --channel stable --source-revision COMMIT --source-date-epoch EPOCH
TRON_BUSYBOX=/absolute/offline/policy-matching-busybox python3 tools/release/c028_release.py check --out release-A --release-id RELEASE --version VERSION --release-sequence N --channel stable --source-revision COMMIT --source-date-epoch EPOCH
python3 tools/release/c028_drills.py self-check
```

The generator builds twice in unrelated checkout/Cargo/target roots and requires identical ELF files, normalized USTAR+gzip archives and OCI manifest/config/layer digests. Verify the DSSE release threshold and anti-rollback floor before enumerating the exact bundle; then verify every size/SHA-256/mode, embedded build identity, OCI descriptors, SPDX 2.3 file/package subjects and DSSE in-toto/SLSA provenance. Reject missing, extra, symlinked, mixed-release or detached material before creating installation staging.

Sapling spend/output appear only as policy records (exact size and BLAKE2b-512, `included=false`, no URL or redistribution claim). Any parameter basename, exact-size parameter candidate, raw fingerprint, SBOM package/component, or bytes in an archive/layer is a release failure. Production private signing keys and trust anchors must not enter source, build jobs, artifacts or images.

The signed manifest fixes all four absolute installation boundaries: `install_prefix=/opt/tron`, `current_target=/opt/tron/current`, `config_root=/etc/tron`, and `receipt_path=/var/lib/tron/install-receipt.json`. Installation creates immutable release-scoped binary and configuration slots, atomically selects them through `/opt/tron/current` and `/etc/tron/current`, and journals recovery across both selectors and the receipt. The receipt separately hashes the exact complete inventories, modes, and relative paths of both immutable slots. Verification rejects a relocated receipt, a different selector, or any missing, extra, or tampered binary/configuration file. Production release, provenance, and root roles each use three independently provisioned keys with threshold two.

## Offline root bootstrap and publication

The provisioned store must define the canonical lowercase role name and scope `release:<channel>` matching the signed manifest channel (for example, both are `release:stable`). The verifier rejects a generic `release` role, a differently cased channel, or a role whose name and scope differ.

Bootstrap the release root out of band from two independently authenticated operator channels. Record its canonical SHA-256 in the protected `release` environment, store the base64-encoded root in `C028_RELEASE_TRUST_ROOT_B64`, and store the independently approved digest in `C028_RELEASE_TRUST_ROOT_SHA256`. The publish job decodes that root into a runner-owned temporary directory and checks the digest before invoking the verifier. A candidate directory, bundle, image, manifest, workflow input, or newly generated release must never supply its own authoritative root.

A release may carry only `release-trust-update.dsse.json`, not an authoritative `release-trust-store.json`. The publish job verifies an update with `verify-trust-update --current` against the externally provisioned current root before extracting or using the candidate root. Rotation is sequential and requires both the current-root and candidate-root thresholds. Publish the newly approved root digest through the same protected environment only after the rotation release is independently verified; retain the preceding root and evidence until the rollback window closes.

For emergency revocation, freeze publication, remove the compromised key from a version+1 trust store, satisfy the uncompromised current threshold plus the new threshold, and distribute the signed update and its digest over independent operator channels. If the current threshold cannot be met, do not accept an in-band candidate root: perform a fresh offline bootstrap under the repository/environment protection break-glass procedure and explicitly reset the minimum trusted version. Run `python3 tools/release/c028_drills.py self-check`; its malicious-candidate drill must report `candidate_root: rejected`.

## Candidate-to-publish workflow handoff

The candidate workflow resolves the canonical lowercase 40-hex source commit, assembles and fully exercises an unsigned candidate in a disposable job with read-only repository permission and no environment, signing keys, signer digest, or other signing secret. It uploads one digest-bound immutable unsigned artifact and stops; candidate-controlled code never invokes signing.

GitHub starts `.github/workflows/c028-release-sign.yml` through `workflow_run` only after a successful `C028 release candidate` `workflow_dispatch`. GitHub loads this workflow definition and its `github.workflow_sha` from the protected default branch, independently of the candidate revision. The approval-gated `c028-release-signing` environment is available only to this signing job. Before secrets are used, the job verifies the triggering run through the Actions API: exact repository and head repository, exact workflow name and path, completed/success status, default head branch, canonical head SHA, and equality with the repository's current default-branch SHA. Fork, pull-request, non-default-branch, stale-head, failed, cancelled, and workflow-name/path-spoofed runs cannot sign.

The signing job checks out only `github.workflow_sha` with submodules and persisted credentials disabled; it never checks out the triggering run's ref, branch, or head SHA. It verifies `tools/release/c028_sign_candidate.py` against the independently provisioned `C028_SIGNER_SOURCE_SHA256`, downloads exactly one non-expired `c028-unsigned-*` artifact from the triggering run ID, verifies the SHA-256 encoded in its name, rejects unsafe archive members, and requires the unsigned manifest source revision to equal the authenticated triggering head SHA. Candidate files remain inert data and are never executed.

### Signer provisioning, rotation, and audit

Provision two independent base64 Ed25519 private keys and their lowercase SHA-256 digests as separate secrets in the protected `c028-release-signing` environment: `C028_RELEASE_SIGNING_KEY_1_B64`, `C028_RELEASE_SIGNING_KEY_1_SHA256`, `C028_RELEASE_SIGNING_KEY_2_B64`, and `C028_RELEASE_SIGNING_KEY_2_SHA256`. Provision the reviewed signer-source digest separately as `C028_SIGNER_SOURCE_SHA256`. Require environment reviewers who cannot bypass branch protection. None of these values may be a workflow input, repository variable, candidate artifact member, or candidate workflow literal.

Rotate signer code by reviewing and merging the new signer on the protected default branch, independently recording its digest, and updating `C028_SIGNER_SOURCE_SHA256` under environment approval. Rotate each key and matching digest as one reviewed pair; never change only the digest or only the private key. Exercise a non-production signing run before approving production use. Roll back code through a reviewed default-branch commit and restore the corresponding recorded digest; roll back keys only as their complete independently authenticated pairs.

The authenticated output contains `c028-candidate.tar.gz` plus `workflow-metadata.json`. The latter is exactly `c028-workflow-metadata-v1`: no missing or additional fields are accepted. It binds `repository`, `candidate_run_id`, `signing_run_id`, `signing_workflow`, `signing_workflow_sha`, `unsigned_artifact_name`, `unsigned_artifact_sha256`, `signed_artifact_name`, `signed_archive_name`, `candidate_sha256`, `release_id`, `channel`, and `source_revision`. `docs/oracles/schemas/c028-workflow-metadata-v1.schema.json` is the canonical Draft 2020-12 schema and `docs/oracles/c028-workflow-metadata.v1.json` is the signer-output-to-publisher fixture. The signing job scrubs keys and extracted candidate data even on failure. Retain those digests, signing key IDs, Actions run records, environment approvers, and scrub outcome for audit; never retain private-key bytes in logs or artifacts.

The publish workflow downloads exactly the approved authenticated artifact name from exactly the protected signing run ID. Before download it queries that run and requires the exact successful `workflow_run` signing workflow name, path, repository, head repository, run ID, workflow SHA, and one non-expired exact-name artifact. It verifies the independently approved candidate SHA-256, then invokes the same strict metadata validator used by the executable fixture tests. The validator cross-checks the signing run, repository, workflow SHA/path, artifact name/digest, authenticated release inventory, channel, source revision, tag, and checkout; any missing, additional, or mismatched metadata field fails. It then fetches only the exact `refs/tags/<release-id>` ref, peels annotated or lightweight tags through `refs/tags/<release-id>^{commit}`, and checks out that commit detached before building the verifier. A branch with the same name cannot substitute for the tag.

Every dispatch value and workflow-run event field consumed by shell steps crosses into the process only through a step `env` entry and is referenced as a quoted shell variable; no untrusted GitHub expression is embedded in shell program text. Candidate assembly, signer secret provisioning, and both publisher jobs require the release ID to match the identical bounded `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$` policy first. The publisher additionally requires the release tag to equal that ID and validates the signing run ID, candidate digest, and digest-bound artifact name before checkout, tag fetch, artifact download, or publication. Empty IDs, leading punctuation, values longer than 128 characters, quotes, command substitutions, newlines, whitespace, leading option markers, and shell metacharacters therefore fail as inert input before artifacts or secrets cross the boundary.
