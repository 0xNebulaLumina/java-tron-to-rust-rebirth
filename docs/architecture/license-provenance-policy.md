# License and provenance policy

C000 establishes the constraints; it does not approve later dependencies, generated code, native components, fixtures, binaries, containers, or distributions.

Every introduced or shipped artifact must have a traceable origin, version or revision, license, copyright notices, generation or modification method, and intended distribution form. Generated code records its generator and inputs. Native libraries and parameters require authenticated sources, integrity verification, redistribution terms, supported architectures, and explicit runtime loading paths. Release artifacts additionally require the SBOM, signed release provenance, and substituted-channel rejection defined by the release gates.

Fixtures use one provenance category: `copied`, `mechanically_derived`, `clean_room`, or `newly_authored`. Copied and mechanically derived material records its upstream source and applicable notices and source obligations. Clean-room work records the behavior-only specification and separation used to avoid copying expressive implementation content. Newly authored work records its origin. The C000 harness fixtures and C001 textproto wire-case inputs are newly authored protocol fixtures; mechanically encoded or mutated C001 binaries inherit those project-authored inputs. The later DR-004 actuator fixture classifies its own content separately.

The pinned `java-tron` source is LGPL-3.0-covered reference material. Repository-local inspection does not automatically permit copying into Rust code or distributed fixtures. Any copied or derived material must preserve applicable notices, identify modifications, and satisfy source-availability and linking obligations for the actual distribution form.

License compatibility is evaluated for the intended use, linkage, modification, notices, source offers, patents, export constraints, and project policy. Missing or ambiguous terms, incompatible obligations, unexplained generated origin, or absent required notices block the consuming item. A content, origin, version, license, generator, input, linkage, or distribution change requires a fresh determination. Legal exceptions must be explicit, scoped, time-bounded, and cannot override law or unknown ownership.

The C001 protocol fixture corpus is governed by `docs/oracles/protocol-fixtures.v1.json`. Every `.textproto` and `.bin` file in `rust-tron/crates/tron-protocol/tests/fixtures/protocol` has an exact in-tree origin revision, content-addressed source inputs, generator or mutation recipe and version, license/notices statement, and distribution intent. ## C005 keystore dependencies and compatibility limits

C005.01-C005.02 add exact, lockfile-pinned pure-Rust releases: `aes` 0.8.4 and `ctr` 0.9.2 for AES-128-CTR, both with their `zeroize` features enabled so the concrete AES-CTR state, including expanded round keys and counter/nonce state, implements zeroizing drop; `scrypt` 0.11.0, `pbkdf2` 0.12.2 with `hmac` 0.12.1 and `sha2` 0.10.9, `serde` 1.0.219 and `serde_json` 1.0.143 for the V3 representation, `subtle` 2.6.1 for constant-time MAC comparison, `uuid` 1.18.1 for V4 identifiers, and `zeroize` 1.8.1 for password-derived and file-input buffers. `libc` 0.2.189 supplies only the Unix `O_NOFOLLOW` flag. These crates and their RustCrypto/transitive dependencies are offered under `Apache-2.0 OR MIT`, `MIT`, or compatible dual terms recorded in Cargo metadata; they introduce no native library or runtime dynamic loading.

The implementation is clean-room code from the behavior-only C005 specification and interoperability observations at pinned java-tron revision `4a21592f95e37908b21bc3f611c6e7a1a67f09f3`; no expressive Java or Bouncy Castle implementation is copied. Unlike Java's unbounded attacker-controlled KDF and field inputs, Rust rejects scrypt parameters outside a legacy-compatible envelope (including both Java standard and light profiles), PBKDF2 iteration counts above 10,000,000, decoded fields above 1 MiB, salts above 1 KiB, and scrypt memory requests above 256 MiB. This reviewed resource-safety deviation preserves all pinned legacy vectors while preventing unbounded CPU, memory, and allocation requests. Any dependency version, feature, limit, source, license, or distribution change requires renewed compatibility and security review.

## C006 shielded-cryptography foundation

The exact direct production dependency/version/declared-feature/resolved-feature/license inventory is machine-readable in `docs/oracles/c006-shielded-provenance.v1.json`. It includes both workspace crates and all crates.io dependencies, notably `bls12_381` 0.8.0 (`MIT OR Apache-2.0`; resolved `alloc,bits,default,group,groups,pairing,pairings`) and `zcash_note_encryption` 0.4.2 (`MIT OR Apache-2.0`; resolved `alloc,default,pre-zip-212`). `Cargo.toml`, Cargo metadata and `Cargo.lock` pin the source graph; any version, declared or resolved feature, source, checksum, or license change reopens C006 license and security review.
