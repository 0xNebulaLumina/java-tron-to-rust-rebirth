# License and provenance policy

C000 establishes the constraints; it does not approve later dependencies, generated code, native components, fixtures, binaries, containers, or distributions.

Every introduced or shipped artifact must have a traceable origin, version or revision, license, copyright notices, generation or modification method, and intended distribution form. Generated code records its generator and inputs. Native libraries and parameters require authenticated sources, integrity verification, redistribution terms, supported architectures, and explicit runtime loading paths. Release artifacts additionally require the SBOM, signed release provenance, and substituted-channel rejection defined by the release gates.

Fixtures use one provenance category: `copied`, `mechanically_derived`, `clean_room`, or `newly_authored`. Copied and mechanically derived material records its upstream source and applicable notices and source obligations. Clean-room work records the behavior-only specification and separation used to avoid copying expressive implementation content. Newly authored work records its origin. The C000 harness fixtures and C001 textproto wire-case inputs are newly authored protocol fixtures; mechanically encoded or mutated C001 binaries inherit those project-authored inputs. The later DR-004 actuator fixture classifies its own content separately.

The pinned `java-tron` source is LGPL-3.0-covered reference material. Repository-local inspection does not automatically permit copying into Rust code or distributed fixtures. Any copied or derived material must preserve applicable notices, identify modifications, and satisfy source-availability and linking obligations for the actual distribution form.

License compatibility is evaluated for the intended use, linkage, modification, notices, source offers, patents, export constraints, and project policy. Missing or ambiguous terms, incompatible obligations, unexplained generated origin, or absent required notices block the consuming item. A content, origin, version, license, generator, input, linkage, or distribution change requires a fresh determination. Legal exceptions must be explicit, scoped, time-bounded, and cannot override law or unknown ownership.

## C001 canonical protocol sources

The 17 files under `rust-tron/crates/tron-protocol/proto/core` and `proto/api` are verbatim copies of `java-tron/protocol/src/main/protos` at java-tron revision `4a21592f95e37908b21bc3f611c6e7a1a67f09f3`. Their relative import layout, file-level notices, upstream `LICENSE`, and upstream `README.md` are retained. They are copied LGPL-3.0-covered source inputs; generated Rust code remains reproducible from these checked-in inputs and the pinned build dependencies.

`rust-tron/crates/tron-protocol/proto/google/protobuf/any.proto` is an immutable verbatim copy from Protocol Buffers tag `v3.25.8`, source URL `https://github.com/protocolbuffers/protobuf/blob/v3.25.8/src/google/protobuf/any.proto`, SHA-256 `bcf5de6ce463b1a38ff76b77955aa7e580b4ec12af34a927b1d45c9efb0faf66`, under BSD-3-Clause terms. The upstream license is retained at `proto/google/LICENSE`. Changing the tag, bytes, digest, include path, or license requires a new provenance and compatibility determination.

The C001 protocol fixture corpus is governed by `docs/oracles/protocol-fixtures.v1.json`. Every `.textproto` and `.bin` file in `rust-tron/crates/tron-protocol/tests/fixtures/protocol` has an exact in-tree origin revision, content-addressed source inputs, generator or mutation recipe and version, license/notices statement, and distribution intent. The textproto cases and the two field-presence byte vectors are original project-authored test data. Canonical binaries are mechanical `libprotoc 28.2` encodings; unknown-field, malformed, and map-order binaries are deterministic mechanical mutations of project-authored canonical inputs. None is copied from or emitted by java-tron. These fixtures are repository test material, not production data or an assertion that constructed Rust map serialization is compatible through direct prost encoding.

Protocol generation is pinned in Cargo manifests and `Cargo.lock` to `prost`/`prost-build` 0.13.5, `tonic`/`tonic-build` 0.12.3, and `protoc-bin-vendored` 3.1.0, all compatible with the workspace Rust 1.85.1 floor. `build.rs` uses the vendored `protoc`, fixes the 17 root inputs and `proto` include root, compiles the vendored `google.protobuf.Any` definition, and enables both tonic clients and servers for all seven canonical service surfaces: `protocol.Wallet`, `protocol.WalletSolidity`, `protocol.WalletExtension`, `protocol.Database`, `protocol.Monitor`, `protocol.Network`, and `protocol.TronZksnark`. Descriptor generation includes imports and source information; normalization then lexicographically sorts `FileDescriptorProto` entries by file name, clears every `source_code_info` field, and re-encodes the set with prost 0.13.5 before byte-comparing it with `descriptors/protocol.v1.pb`. `descriptors/protocol.v1.json` and `docs/oracles/protocol-conformance.v1.json` record this same generator configuration, normalization contract, and service inventory. Generated Rust source is build output rather than copied Java implementation code; the checked-in descriptor is distributed with its generation inputs and metadata.

## C004 pure-Rust cryptography dependencies

C004.01-C004.03 use exact, lockfile-pinned RustCrypto releases compatible with the Rust 1.85.1 floor: `k256` 0.13.4 for secp256k1 arithmetic and ECDSA, `sm2` 0.13.3 for standard-curve arithmetic, `sha2` 0.10.9, `sm3` 0.4.2, `sha3` 0.10.8 (legacy `Keccak256`/`Keccak512` types only), and `ripemd` 0.1.3. These crates are pure Rust and offered under `Apache-2.0 OR MIT`; their transitive RustCrypto arithmetic, digest, signature, and encoding crates retain their upstream license metadata in the Cargo registry and lockfile. `base64` 0.22.1 (`MIT OR Apache-2.0`) and `rand_core` 0.6.4 (`MIT OR Apache-2.0`) provide encoding and operating-system/test-injected randomness boundaries. No native library, runtime dynamic loading, copied Java implementation, or keystore component is introduced.

The implementation is clean-room code based on the behavior-only C004 specification and interoperability observations from pinned java-tron revision `4a21592f95e37908b21bc3f611c6e7a1a67f09f3`. The Java source remains LGPL-3.0 reference material and no expressive Java or Bouncy Castle implementation content is copied. The SM2 crate documents that its arithmetic has not received an independent third-party audit; C004 therefore limits it to the standard curve arithmetic behind typed TRON compatibility APIs, records this review finding, and does not represent the dependency as independently audited. A dependency version, feature set, source, license, or distribution change requires renewed compatibility and security review.

The C004 interoperability artifact `docs/oracles/c004-crypto-fixture-manifest.v1.json` is mechanically derived by the Java 8-compatible `tools/crypto/C004Oracle.java` oracle. The gate compiles that newly authored oracle against the checked-in `java-tron` gitlink at revision `4a21592f95e37908b21bc3f611c6e7a1a67f09f3` and Bouncy Castle `org.bouncycastle:bcprov-jdk18on:1.84`; it authenticates both the upstream JAR (SHA-256 `64d6c5a6121fcd927152dd182cbed39afe0fda641a970d9bcc0c9cb1858b2731`) and its Gradle/Maven POM metadata (SHA-256 `ce7abb4a91ba5d2a73fdf17a3df4762e3605a0392cc7983ef2f1ae16cd384cc3`) before execution. Bouncy Castle is MIT-licensed. The generated JSON contains fixed public values and behavioral results, not copied Java or Bouncy Castle implementation source; it is test-only interoperability material and is regenerated or byte-verified by `tools/crypto/c004_oracle.py`. Changing the Java revision, oracle source, dependency coordinates, authenticated bytes, vector inputs, output schema, or distribution intent requires renewed provenance and compatibility review.
